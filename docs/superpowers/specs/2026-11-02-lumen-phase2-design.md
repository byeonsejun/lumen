# LUMEN 2차 — 담기 · 내 방 장바구니 · 로그인 · 토스 테스트 결제 · 주문 내역

- 작성일: 2026-11-02
- 상태: 사용자 검토 대기 (구현자 관점 점검 완료 — 데모 계정 질문 1건 반영)
- 1차 설계: [`2026-11-02-lumen-design.md`](./2026-11-02-lumen-design.md) — 그 문서의 전역 제약(렌더러 · 출처 표기 · 성능 목표)은 그대로 이어진다

## 1. 왜 하는가

1차는 둘러보기만 되는 3D 쇼룸이다. 2차는 실제로 주문까지 되는 쇼핑몰로 만든다.

**사용자 결정: 2차가 보여 줄 것은 "3D 쇼핑 경험이 구매까지 이어진다"는 점이다.** 결제를 탄탄하게 만드는 능력은
포트폴리오의 Nextour 가 이미 깊게 보여 준다(2단계 결제 · 환불 saga · 멱등성). 같은 이야기를 두 번 하지 않는다.

면접관이 데모를 보는 1~2분 안에 하나의 이야기가 끝까지 이어져야 한다:
**3D 로 보고 → 그 자리에서 담고 → 담은 가구가 놓인 내 방을 보고 → 결제하면 그 가구 위로 불이 켜진다.**

## 2. 목표 · 비목표 · 실패 조건

### 목표 (사용자 확정)
1. **담는 순간** — 쇼룸에서 둘러보다가, 상세에서 돌려 보다가 페이지를 떠나지 않고 바로 담는다
2. **장바구니 = 내 방 미리보기** — 담은 가구가 한 방에 **자동으로** 놓인 3D 장면 + 평범한 목록 · 합계
3. **결제 완료** — 어두운 방에서 방금 산 가구 위로 조명이 하나씩 켜지며 주문 번호가 뜬다
4. **로그인 · 결제 · 주문 내역은 평범하게** — 카카오 · 구글 로그인, 토스 테스트 결제, 주문 목록

### 비목표
- 환불 · 주문 취소 · 결제 웹훅 · 부분 결제 (Nextour 가 보여 준다)
- 재고 · 배송 추적 · 쿠폰 · 이메일 · 관리자
- **가구를 직접 옮기기 · 방 크기 입력** — 3차 "내 방에 놓아 보기" 로 (사용자 확정 · 4.3)
- 실결제. 토스 **테스트 키만** 쓴다

### 실패 조건 (돌아가도 실패인 것)
- **로그인 전에 담은 가구가 로그인 뒤 사라진다**
- **화면에 보인 금액과 결제되는 금액이 다르다**, 또는 브라우저에서 금액을 바꿔 덜 낼 수 있다
- **결제 완료 페이지를 새로고침하면 결제가 두 번 승인된다**
- 3D 때문에 주문서 작성 · 결제 화면이 느려진다 → **주문서(checkout) 화면에는 3D 를 두지 않는다**
- 1차의 성능 기준이 무너진다 — 상품 상세 · 쇼룸은 지금처럼 정적으로 빠르게. 로그인 여부를 읽느라 정적 페이지가 동적으로 바뀌면 실패

## 3. 흐름

```
[쇼룸 · 상세] ──담기──▶ (헤더 장바구니 수 +1 · "담았어요 · 장바구니 보기" 토스트)
       │
       ▼
[/cart] 내 방(3D) + 목록 ── 주문하기 ──▶ 로그인 안 했으면 [/login] → 돌아오며 장바구니 합치기
       │
       ▼
[/checkout] 받는 사람 · 연락처 · 주소(가짜) + 토스 결제 위젯   ← 3D 없음
       │ 토스 결제창(테스트)
       ├─ 성공 ▶ [/checkout/success] 서버가 금액 검증 · 승인 · 주문 PAID · 장바구니 비움
       │          ▶ [/orders/{id}/complete] 불이 켜지는 장면 + 주문 번호
       └─ 실패 ▶ [/checkout/fail] 사유 + "다시 시도" (장바구니 그대로)

[/orders] 내 주문 목록 → [/orders/{id}] 주문 상세 (3D 없음)
```

## 4. 화면

### 4.1 담기 — 3D 에서 바로
- **쇼룸 스포트라이트 오버레이**: `자세히 →` 옆에 `담기`
- **쇼룸 둘러보기(explore)**: 가구 이름표 옆에 작은 `+` 버튼. 이름표 자체는 지금처럼 상세로 간다
- **상품 상세**: 1차의 비활성 `장바구니 담기 (준비 중)` 를 살린다. 수량 선택(1~9)
- 담으면: 헤더에 장바구니 수 배지, 화면 아래 토스트 `담았어요 · 장바구니 보기`. 페이지는 그대로
- 1차의 비활성 `내 방에 놓아 보기 (준비 중)` 버튼은 **3차까지 그대로 둔다**

### 4.2 장바구니 `/cart` — 좌우 나누기 (사용자 선택: 시안 A)
- **왼쪽(약 60%) 3D 방**: 담은 가구가 4.3 규칙으로 놓인 방. 드래그로 둘러보기(쇼룸 explore 와 같은 제한). 터치 기기는 1차처럼 자동 왕복
- **오른쪽 목록**: 썸네일 · 이름 · 가격 · 수량(−/+) · 삭제, 아래에 합계와 `주문하기`
- **목록 ↔ 방 연결**: 목록 행에 마우스를 올리거나 누르면 방에서 그 가구에 스포트라이트가 떨어지고 나머지는 어두워진다. 방에서 가구를 누르면 목록의 그 행이 강조된다
- **모바일**: 방이 위(화면 높이의 약 45%), 목록이 아래
- **빈 장바구니**: 빈 방에 스포트라이트 하나 + `아직 담은 가구가 없어요` + 쇼룸 · Shop 링크
- 품질 단계 · 폴백(WebGPU → WebGL2 → 이미지)은 1차 `Stage3D` 를 그대로 쓴다. 이미지 폴백일 땐 방 대신 목록만 넓게

### 4.3 내 방 자동 배치 (Claude 제안 · 사용자 동의)
담긴 것이 무엇이 몇 개든 방에 알아서 놓는다. **직접 옮기기는 하지 않는다**(3차).

- 규칙 (우선순위 순):
  1. **큰 가구**(소파 · 침대 · 선반)는 벽을 따라 등을 벽에 붙인다. 뒷벽 → 왼쪽 벽 → 오른쪽 벽 순
  2. **테이블**은 가운데. 여러 개면 가운데 줄로 나란히
  3. **의자 · 오토만**은 테이블 주변(테이블이 없으면 소파 앞)
  4. **조명**: 펜던트 · 샹들리에는 천장(테이블 위가 비었으면 그 위), 캔들 홀더는 테이블이나 선반 위
  5. **소품**(화분 · 화병): 화분은 구석 바닥, 화병은 테이블 · 선반 위(없으면 바닥 구석)
- 크기는 상품의 실제 치수(`dimensionsMm`)로 계산한다. 가구끼리 겹치지 않는다
- 가구가 많아 자리가 모자라면 **방이 넓어진다**(기본 4m × 4m 에서 시작해 0.5m 씩)
- 같은 가구를 여러 개 담으면 **최대 4개까지 실제로 놓고**, 그 이상은 4번째에 `×N` 라벨
- 순수 함수로 만든다: 입력(장바구니 항목들) → 출력(방 크기 + 각 가구의 위치 · 회전). 같은 입력엔 항상 같은 배치
- 3차의 "직접 옮기기" 는 이 결과를 시작 배치로 쓴다

### 4.4 로그인 `/login`
- 카카오 · 구글 두 가지 (Claude 제안 — Nextour 코드 재사용)
- **`데모 계정으로 체험하기` 버튼 (사용자 확정)** — 면접관이 개인 계정으로 로그인하지 않고도 담기부터 결제 완료 장면까지 끝까지 가 볼 수 있게 한다
  - 누르면 **그 브라우저 전용 임시 계정**을 만들어 바로 로그인한다(Claude 판단: 공용 계정 하나를 쓰면 여러 사람의 장바구니 · 주문이 섞인다)
  - 화면 헤더에 `데모 계정` 표시. 결제는 어차피 테스트 키라 실제 돈은 나가지 않는다
  - 만든 지 24시간 지난 데모 계정은 장바구니 · 주문과 함께 지운다(새 데모 계정을 만들 때 오래된 것을 정리)
  - 장바구니 화면의 `주문하기` 에서 로그인으로 보낼 때도 이 버튼이 맨 위에 보인다
- 장바구니에서 `주문하기` 를 눌렀는데 로그인 전이면 로그인으로 보내고, 끝나면 `/checkout` 으로 돌아온다
- 헤더: 로그인 전 `로그인`, 로그인 후 이름 + `내 주문` · `로그아웃`

### 4.5 주문서 `/checkout` — 3D 없음
- 주문 상품 요약(썸네일 · 이름 · 수량 · 소계) · 합계
- 받는 사람 · 연락처 · 주소 입력 (가짜 데이터임을 화면에 밝힌다: `테스트 결제입니다. 실제 배송되지 않아요`)
- 토스 결제 위젯 → `결제하기`

### 4.6 결제 완료 `/orders/{id}/complete`
- 어두운 방(4.3 배치, 이번에 산 가구만) → 0.4초 간격으로 가구마다 조명이 켜진다 → 마지막에 방 전체 조명
- 화면 아래: `주문이 완료됐어요` · 주문 번호 · 합계 · `주문 내역 보기`
- `prefers-reduced-motion` 이면 처음부터 다 켜진 상태
- 새로고침해도 결제를 다시 하지 않는다(승인은 `/checkout/success` 에서만, 이미 PAID 면 건너뛴다)

### 4.7 주문 내역 `/orders` · `/orders/{id}`
- 목록: **결제 완료된 주문만** 보여 준다 — 주문일 · 대표 상품명 외 N건 · 합계. `주문하기` 를 누를 때마다 PENDING 주문이 새로 생기므로, 결제 대기 · 실패 주문까지 보이면 목록이 지저분해진다
- 상세: 상품 목록(주문 당시 이름 · 가격) · 받는 사람 · 결제 수단(토스 응답의 method) · 승인 시각
- 내 주문만 보인다. 남의 주문 id 로 들어오면 404

## 5. 데이터

### 5.1 상품은 계속 코드에
상품 정보는 1차처럼 `src/catalog/products.ts` 에 둔다. **DB 에 상품 테이블을 만들지 않는다.**
대신 **가격은 언제나 서버에서 카탈로그로 다시 계산**한다. 브라우저가 보낸 가격은 믿지 않는다.

### 5.2 테이블 (Prisma)
- Auth.js 표준: `User` · `Account` · `Session` · `VerificationToken`
- `CartItem` — userId · productSlug · quantity(1~9) · 수정 시각. (userId, productSlug) 유일
- `Order` — id(토스 orderId 로도 쓴다, 추측 어려운 값) · userId · status(`PENDING` · `PAID` · `FAILED`) ·
  totalKRW · orderName(예: `Ember 3인 소파 외 2건`) · 받는 사람 · 연락처 · 주소 · paymentKey · method · paidAt · createdAt
- `OrderItem` — orderId · productSlug · **주문 당시** 이름 · 가격 · 수량

### 5.3 로그인 전 장바구니
- 로그인 전: 브라우저 저장소(localStorage)에 둔다. 서버를 부르지 않아 정적 페이지가 그대로 빠르다
- 로그인 순간: 브라우저 장바구니를 서버로 보내 **합친다**. 같은 상품은 수량을 더하고 9 에서 자른다. 카탈로그에 없는 slug 는 버린다. 합친 뒤 브라우저 쪽은 비운다
- 로그인 후: 서버가 기준. 화면은 낙관적으로 먼저 바꾸고 서버 결과로 맞춘다

## 6. 결제 (토스 테스트) — 가볍게, 그러나 돈이 틀리면 안 된다

1. `주문하기` → 서버가 **카탈로그 가격으로 합계를 계산**해 `Order(PENDING)` + `OrderItem` 을 만든다
2. 위젯 `requestPayment({ orderId, amount: 서버가 계산한 합계, successUrl, failUrl })`
3. `/checkout/success?paymentKey&orderId&amount`:
   - 주문이 내 것인지, `amount` 가 저장된 totalKRW 와 같은지 확인. 다르면 승인하지 않고 FAILED
   - 이미 PAID 면 승인을 다시 부르지 않고 완료 화면으로
   - 토스 승인 API 호출(Idempotency-Key = orderId) → 성공이면 PAID · paymentKey · method · paidAt 저장 · 장바구니 비움
4. `/checkout/fail`: 토스가 준 사유를 보여 주고 `다시 시도`. 장바구니는 그대로

- 토스 클라이언트 · 에러 처리는 Nextour `src/shared/lib/toss/client.ts` 를 가져온다 (환불 · 웹훅 부분은 가져오지 않는다)
- **결제 시뮬레이션 모드**: 운영이 아닐 때(로컬 · e2e) 토스 결제창을 건너뛰고 success 로 같은 파라미터를 붙여 이동, 승인도 가짜 응답. Nextour `PaymentWidget.tsx` 의 `devFallback` 과 같은 방식

## 7. 만드는 방식

### 고려한 것
| | A. Auth.js + Prisma + Postgres | B. Supabase(로그인 + DB) | C. A + 장바구니도 항상 서버 |
|---|---|---|---|
| 장점 | Nextour 의 로그인 · 결제 · DB 코드를 거의 그대로. 시간을 장바구니 방과 완료 연출에 쓴다 | 코드가 가장 적고 새 기술(Supabase · RLS) 하나 추가 | 기기를 바꿔도 장바구니 유지, 합치기 불필요 |
| 단점 | 로그인 순간 장바구니 합치기 처리가 하나 생긴다 | Nextour 코드를 못 쓰고 새로 익힌다 — 2차의 목표와 다른 곳에 시간을 쓴다 | 담을 때마다 서버 왕복, 정적 페이지에 서버 의존. Cache Components 와 부딪히는 곳이 늘어난다 |

### 고른 것: **A** (사용자 선택)
- DB: **Neon Postgres** — Vercel Marketplace 로 `lumen` 프로젝트에 붙인다(무료 구간)
- 로그인: Auth.js v5 · Prisma 어댑터 · Kakao · Google · JWT 세션(Nextour 와 같은 설정)
- 결제: `@tosspayments/tosspayments-sdk` v2 결제 위젯 · 테스트 키

### Next.js 16 Cache Components 와의 경계
- 쇼룸 · Shop · 상품 상세는 **지금처럼 정적**이다. 헤더의 로그인 상태 · 장바구니 수는 클라이언트 컴포넌트가 읽는다
- `/cart` · `/checkout` · `/orders` 는 세션을 읽는 부분만 `<Suspense>` 안에 둔다
- 로그인이 필요한 경로의 차단과 남의 주문 404 는 서버에서 판단한다(1차의 404 처럼, 응답이 시작되기 전에)

## 8. 사용자 계정 작업 (구현 중 안내)
1. Vercel 대시보드 → `lumen` → Storage/Marketplace 에서 Neon 연결 (`DATABASE_URL` 자동 등록)
2. 카카오 개발자 앱 · 구글 OAuth 클라이언트에 Redirect URI 추가:
   `https://lumen-showroom.vercel.app/api/auth/callback/{kakao,google}` 와 `http://localhost:3000/...`
   — Nextour 에서 쓰던 앱에 주소만 더해도 되고, 새로 만들어도 된다
3. 토스 테스트 키(클라이언트 · 시크릿) — Nextour 테스트 키 재사용 가능
4. `AUTH_SECRET` 생성 (데모 계정은 별도 키가 필요 없다)

## 9. 테스트
- 단위: **자동 배치**(겹침 없음 · 같은 입력 같은 출력 · 방 확장 · ×N), **장바구니 합치기**, **금액 계산과 검증**(조작된 amount 거부), 주문 상태 전이(이미 PAID 면 재승인 안 함)
- e2e: 담기 → 장바구니 방 → 주문 → (시뮬레이션) 결제 → 완료 화면 → 주문 내역. 로그인 전 담은 것이 로그인 뒤 남는지. 남의 주문 404
- **e2e 로그인은 데모 계정 버튼을 그대로 쓴다** — 운영에도 있는 경로라 테스트 전용 뒷문이 필요 없다
- 데모 계정 단위 테스트: 브라우저마다 다른 계정 · 24시간 지난 데모 계정 정리 · 데모 계정은 카카오/구글 계정과 섞이지 않음

## 10. 구현자에게 맡기는 것
- 토스트 · 배지 · 수량 버튼 등 세부 UI
- 자동 배치의 세부 간격 값(벽과의 거리, 의자-테이블 거리 등)
- 장바구니 클라이언트 상태 도구(1차의 zustand 권장)
- 데모 계정을 Auth.js 에 붙이는 방식(Credentials 프로바이더 등)과 정리 시점 세부
- `orderName` 형식 세부

## 11. Claude 가 정한 것 (사용자 검토용)
- 로그인 제공자: 카카오 · 구글 (Nextour 재사용)
- 상품은 DB 에 넣지 않고 서버에서 카탈로그로 가격을 다시 계산 (5.1)
- 로그인 전 장바구니는 브라우저, 로그인 순간 합치기 · 수량 상한 9 (5.3)
- 같은 가구는 최대 4개까지 실제로 놓고 이후는 ×N (4.3)
- 방은 4m × 4m 에서 시작해 0.5m 씩 넓어짐 (4.3)
- 주문서 화면엔 3D 없음 (2장 실패 조건)
- 웹훅 없이 success 리다이렉트에서 승인 (6장) — 테스트 결제라 충분하고, 웹훅은 Nextour 가 보여 준다
- 결제 실패 시 장바구니 유지, 주문은 FAILED 로 남김
- 주문 id 를 토스 orderId 로 겸용
- 데모 계정은 브라우저마다 임시 계정 · 24시간 뒤 정리 (4.4)
- 주문 내역엔 결제 완료(PAID) 주문만 (4.7). PENDING · FAILED 는 DB 에만 남는다
- Vercel 미리보기 배포 주소에선 OAuth 리다이렉트가 안 맞으므로, 로그인 확인은 운영 주소와 localhost 에서만 한다
